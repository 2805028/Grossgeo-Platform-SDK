# GrossGeo Publishing API — выпуск релизов из своей утилиты

> Для разработчиков продуктов GrossGeo. Позволяет собирать и публиковать релизы из собственного
> скрипта или CI, не открывая Developer Panel.
>
> Машиночитаемая спецификация: `GET {BASE_URL}/swagger/public-v1/swagger.json`

---

## 1. Что нужно знать до начала

Публикация — это шесть HTTP-вызовов: создать черновик релиза, получить ссылку на загрузку,
залить артефакт, зарегистрировать его, отправить на выпуск. Всё остальное (проверка контрольной
суммы, разбор `release-manifest.json`, подпись манифеста) делает сервер — приватных ключей на
вашей стороне не нужно.

Две вещи, которые экономят полдня, если узнать о них заранее:

- **Артефакт загружается напрямую в объектное хранилище** по временной ссылке, а не через API.
  Загрузка через API ограничена 2.5 МБ на уровне шлюза, поэтому для реального дистрибутива она
  не работает — это не оптимизация, а единственный путь.
- **`Content-Type` участвует в подписи ссылки.** Если при загрузке отправить не тот тип, который
  вы указали при запросе ссылки, хранилище ответит `403 SignatureDoesNotMatch`. Ошибка выглядит
  как проблема доступа, а на деле это несовпадение заголовка.

## 2. Токен

Токен выпускает **владелец студии** в Developer Panel → «API-токены». Полный токен показывается
один раз при выпуске; сервер хранит только его хеш и восстановить значение не может. Если токен
потерян — выпустите новый и отзовите старый.

```
Authorization: Bearer ggp_1a2b3c4d_<секрет>
```

**Срок жизни** — по умолчанию 90 дней, максимум 365; бессрочных токенов не бывает. Планируйте
ротацию: истёкший токен отвечает `401`, и пайплайн встанет.

**Права (скоупы)** выдаются при выпуске. Токен без скоупа не может ничего.

| Скоуп | Что открывает |
|-------|---------------|
| `releases:read` | список и карточка релиза, статус модерации |
| `releases:write` | создать и править черновик, ссылки на загрузку, регистрация и удаление файлов |
| `releases:submit` | отправить релиз на выпуск и отозвать его |
| `products:read` | продукты, планы, функции, категории, теги, лимиты, профиль студии |
| `products:write` | создание и правка продукта, иконка, скриншоты |
| `plans:write` | планы, функции, лимиты, импорт `plans-manifest` |
| `pricing:write` | цены и платные условия: правка цен продуктов и тарифов, `TrialDays`, `MaxSeats > 1`, валюта кроме RUB, режимы `ExternalOnly` и `ExternalLicense`, цена для показа, ссылка покупки |

**Про `releases:submit` отдельно.** Если студия прошла верификацию, отправка релиза публикует его
пользователям **немедленно, без проверки человеком**. Если такое поведение в автоматическом
пайплайне нежелательно, не выдавайте этот скоуп: токен соберёт и зальёт релиз, а публикацию
сделает человек в панели. Исключения — всегда модератор, у любой студии: выпуск с новой редакцией
лицензионного соглашения ([руководство по соглашению](grossgeo-product-agreement-guide.md#6-модерация))
и любой выпуск продукта в режиме «Внешняя лицензия» ([раздел 7](#7-режим-внешняя-лицензия)).

**Про `pricing:write` отдельно.** Базовые `products:write` и `plans:write` меняют продукты,
тарифы и функции, **кроме цен**. Любой запрос, тело которого несёт денежные поля (цены,
`TrialDays`, `MaxSeats > 1`, валюта кроме RUB, переход в `ExternalOnly` или `ExternalLicense`,
цена для показа `externalPrice` или её стирание, ссылка покупки `externalPurchaseUrl`), требует также
`pricing:write` — иначе `403 TOKEN_SCOPE_REQUIRED`. Токенам, выданным до введения этого скоупа,
он добавлен автоматически, если у них были `products:write` или `plans:write`; для CI-токена,
которому цены не нужны, не выдавайте `pricing:write` при выпуске нового токена. Импорт
`plans-manifest` с ценами в **новых** тарифах тоже требует `pricing:write` — при этом
повторный прогон того же манифеста работает и без него (уже существующие тарифы не трогаются).

**Ключи функций (`secrets:*`).** Ключевой материал функции (см. руководство разработчика SDK, раздел
«Ключевой материал возможности») заводится и читается через Developer API, база —
`/api/developer/products/{productId}/features/{featureCode}/keys`. `secrets:write` — завести версию
ключа (`POST …/keys`, тело `{"kid":"2026-09"}`) и вывести её из обращения (`POST …/keys/{kid}/retire`);
`secrets:read` — список версий (`GET …/keys`) и материал (`GET …/keys/{kid}/material`). Материал
отдаётся только токену: сессия разработчика получает `403 TOKEN_REQUIRED`. **Отзыв версии**
(`POST …/keys/{kid}/revoke`) токену недоступен (`403`) — только владелец студии сессией: действие
необратимо и ломает у пользователей уже установленные релизы.

**Чего токен не может** независимо от набора скоупов: выплаты и финансовые отчёты, управление
командой студии, правка профиля студии, подписка на листинг, отзывы, тикеты поддержки, удаление
и архивация продукта, выпуск других токенов. Это ограничение маршрутов, а не прав: такие запросы
получают `403 TOKEN_ROUTE_FORBIDDEN`.

Храните токен как пароль — в секретах CI, не в репозитории. Скомпрометированный токен отзывается
мгновенно в той же панели.

## 3. Полный цикл

Ниже `BASE_URL` — адрес платформы, `TOKEN` — ваш токен, `PRODUCT_ID` — идентификатор продукта
(виден в адресной строке карточки продукта в Developer Panel).

### Шаг 1. Создать черновик релиза

```bash
curl -sS -X POST "$BASE_URL/api/developer/products/$PRODUCT_ID/releases" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version":"1.4.0","channel":"Stable","distributionType":"Bundle",
       "changelog":"Исправлена выгрузка профилей"}'
```

Ответ `201`: `{"releaseId":"…"}`.

Версия нормализуется до четырёх компонентов: `1.4.0` сохранится как `1.4.0.0`.

**`distributionType` указывайте явно.** Он определяет, какое расширение файла релиз примет, и по
умолчанию равен `PluginDll` — то есть только `.dll`. Забытое поле проявится не здесь, а на шаге 2
отказом `INVALID_EXTENSION`, что читается как проблема с файлом, хотя дело в типе релиза.

| `distributionType` | Допустимое расширение |
|--------------------|-----------------------|
| `PluginDll` | `.dll` |
| `Bundle` | `.zip` |
| `Installer` | `.msi` |

**`targetPlatforms` тоже указывайте явно, и на каждом релизе заново.** В Developer Portal форма нового релиза
подставляет платформы последнего опубликованного релиза того же продукта; при публикации через этот API
такого наследования нет (`LGC-1407`). Забытое поле не даёт отказа — сервер молча записывает `["AutoCAD"]`,
и релиз остаётся объявлен только для AutoCAD, даже если предыдущий релиз указывал больше платформ:

```bash
curl -sS -X POST "$BASE_URL/api/developer/products/$PRODUCT_ID/releases" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version":"1.4.0","channel":"Stable","distributionType":"Bundle",
       "targetPlatforms":["AutoCAD","Civil3D"],
       "changelog":"Исправлена выгрузка профилей"}'
```

Отдельно от этого всегда принимается `release-manifest.json` (тип файла `ReleaseManifest`).

**`agreementRevisionId` — лицензионное соглашение выпуска.** Не переданное поле означает редакцию
последнего выпуска продукта, у которого соглашение было; `"00000000-0000-0000-0000-000000000000"` —
выпуск без соглашения. В пайплайне передавайте поле явно.
Как создать редакцию и что увидит участник — [Лицензионное соглашение продукта в User Panel](grossgeo-product-agreement-guide.md).

Если версия уже занята, вернётся `400` с кодом `VERSION_EXISTS` — **и с идентификатором занявшего
её релиза**:

```json
{
  "status": 400,
  "code": "VERSION_EXISTS",
  "detail": "Версия 1.4.0.0 уже существует (релиз 6f1a…, статус Draft)",
  "releaseId": "6f1a…"
}
```

Это сделано ради перезапуска пайплайна: если предыдущий прогон успел создать черновик и упал
дальше, продолжайте работу с этим `releaseId`, а не начинайте заново.

### Шаг 2. Запросить ссылку на загрузку

```bash
curl -sS -X POST "$BASE_URL/api/developer/releases/$RELEASE_ID/files/upload-url" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"fileName":"MyPlugin.zip","fileType":"Bundle","fileSizeBytes":52428800}'
```

Ответ: `{"uploadUrl":"https://…","storagePath":"releases/<releaseId>/MyPlugin.zip"}`.

Ссылка живёт ограниченное время (по умолчанию 15 минут). Повторный запрос **безопасен**: путь
объекта определяется именем файла, поэтому вы получите новую ссылку на тот же объект. Если
загрузка большого файла не уложилась в срок — просто запросите ссылку снова.

### Шаг 3. Залить артефакт напрямую в хранилище

```bash
curl -sS -X PUT "$UPLOAD_URL" \
  -H "Content-Type: application/octet-stream" \
  --data-binary "@MyPlugin.zip"
```

`Content-Type` обязан совпадать с тем, что подписан в ссылке (`application/octet-stream`, если
вы не задавали иного). Несовпадение → `403 SignatureDoesNotMatch` от хранилища.

Потолок размера — **100 МБ**. Он проверяется на следующем шаге, по метаданным объекта: файл
больше лимита будет удалён из хранилища, а регистрация отклонена.

### Шаг 4. Зарегистрировать файл

```bash
curl -sS -X POST "$BASE_URL/api/developer/releases/$RELEASE_ID/files/register" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"storagePath":"releases/'"$RELEASE_ID"'/MyPlugin.zip","fileType":"Bundle"}'
```

Сервер скачивает объект, считает `sha256`, определяет размер и — для ZIP-бандлов — разбирает
`release-manifest.json` из корня архива и проверяет его по JSON-схеме. Невалидный манифест даёт
`400` с перечнем ошибок в поле `errors.manifest`, а сам объект удаляется из хранилища.

**Повторный вызов безопасен**: регистрация идемпотентна по пути объекта. Если вы не получили
ответ из-за обрыва связи — повторите, дубликата не появится.

### Шаг 5. Отправить релиз

```bash
curl -sS -X POST "$BASE_URL/api/developer/releases/$RELEASE_ID/submit" \
  -H "Authorization: Bearer $TOKEN"
```

Требует скоупа `releases:submit`. Ответ содержит `autoApproved`: `true` — релиз уже опубликован
пользователям, `false` — ушёл на модерацию.

Релиз обязан содержать хотя бы один файл дистрибутива (`Plugin`, `Bundle` или `Installer`),
иначе `400 NO_DISTRIBUTION_FILE`.

### Шаг 6. Дождаться вердикта (если модерация)

Вебхуков наружу пока нет — опрашивайте карточку релиза:

```bash
curl -sS "$BASE_URL/api/developer/releases/$RELEASE_ID" \
  -H "Authorization: Bearer $TOKEN"
```

Поле `status`: `Draft` → `PendingReview` → `Published` либо `Rejected` (тогда причина в
`rejectionReason`). Разумный интервал опроса — минуты, не секунды: проверка выполняется человеком.

## 4. Перезапуск пайплайна

Сбой в середине — нормальная ситуация, и API рассчитан на повтор:

| Ситуация | Что делать |
|----------|-----------|
| Черновик уже создан | Взять `releaseId` из тела ошибки `VERSION_EXISTS` |
| Неизвестно, создан ли черновик | `GET /api/developer/products/{productId}/releases?version=1.4.0` — точный фильтр по версии |
| Ссылка на загрузку истекла | Запросить заново, тот же путь объекта |
| Неясно, зарегистрирован ли файл | Повторить регистрацию: она идемпотентна |
| Версия занята отозванным релизом | Отозванные и отклонённые версии освобождаются — создание пройдёт |

Отдельный флаг: править релиз (`PUT /api/developer/releases/{id}`) можно только с заголовком
`If-Match`, значение которого берётся из `ETag` предшествующего `GET`. Без него ответ —
`428 Precondition Required`. Это защита от одновременной правки из панели и из скрипта.

## 5. Ограничения и особенности

- **Лимит запросов** — 300 в минуту на токен. При превышении `429` с заголовком `Retry-After`;
  в успешных ответах есть `X-RateLimit-Remaining`.
- **Холодный старт.** Платформа работает на serverless-контейнерах: первый запрос после паузы
  может занять несколько секунд. Ставьте таймаут с запасом и повторяйте запрос при сетевой
  ошибке — но только идемпотентные шаги (см. таблицу выше).
- **Загрузка через API (`/files/upload`, multipart)** существует, но снаружи бесполезна: шлюз
  режет тело на 2.5 МБ. Официальный путь — presigned-ссылка. В публичной спецификации этого
  маршрута нет.
- **Формат ошибок** — RFC 7807 (`application/problem+json`). Машинный код всегда в поле `code`,
  человекочитаемое пояснение — в `detail`. Часть ответов дополнительно несёт `errors` со списком
  проблем валидации.

### Коды, которые стоит обработать явно

| Код | Статус | Значение |
|-----|--------|----------|
| `VERSION_EXISTS` | 400 | версия занята; `releaseId` в теле |
| `NO_DISTRIBUTION_FILE` | 400 | в релизе нет файла дистрибутива |
| `MANIFEST_INVALID` | 400 | `release-manifest.json` не прошёл схему; детали в `errors.manifest` |
| `TARGET_PLATFORM_UNKNOWN` | 400 | в `targetPlatforms` незнакомая платформа (создание и правка релиза); допустимые значения названы в тексте отказа: `AutoCAD`, `Civil3D`, `Map3D`, `Architecture`, `Mechanical`, `Electrical`, `MEP`, `Plant3D` |
| `FILE_NOT_IN_S3` | 400 | регистрация до успешной загрузки |
| `INVALID_STATUS` | 400 | операция не для текущего статуса релиза |
| `TOKEN_SCOPE_REQUIRED` | 403 | токену не хватает скоупа |
| `TOKEN_ROUTE_FORBIDDEN` | 403 | маршрут недоступен токенам в принципе |
| `PRICING_SCOPE_REQUIRED` | 400 | импорт `plans-manifest` несёт цены в новых тарифах, а токену не хватает `pricing:write`; тарифы поимённо в тексте отказа |
| `EXTERNAL_ONLY` | 400 | импорт `plans-manifest` продукту в режиме `ExternalOnly` — тарифные планы и функции такому продукту не положены |
| `AGREEMENT_REVISION_NOT_FOUND` | 400 | `agreementRevisionId` создания или правки релиза — не редакция соглашения этого продукта |
| `INSTALLER_ONLY` | 400 | продукт в режиме `ExternalLicense`: релиз не MSI (создание, правка, отправка) |
| `EXTERNAL_LICENSE_NO_BETA` | 400 | продукт в режиме `ExternalLicense`: канал `Beta` недоступен |
| `EXTERNAL_LICENSE` | 400 | продукт в режиме `ExternalLicense`: тарифы, функции и импорт `plans-manifest` не положены |
| — | 401 | токен неверен, отозван или истёк |
| — | 428 | `PUT` релиза без `If-Match` |

Отозванный, истёкший и несуществующий токен неразличимы в ответе — все дают `401` без
подробностей. Это сделано намеренно.

## 6. Пример на PowerShell

```powershell
$ErrorActionPreference = 'Stop'
$base    = $env:GROSSGEO_BASE_URL
$headers = @{ Authorization = "Bearer $env:GROSSGEO_TOKEN" }

# 1. Черновик (или переиспользование существующего)
$body = @{
    version          = '1.4.0'
    channel          = 'Stable'
    distributionType = 'Bundle'
    changelog        = 'Исправлена выгрузка профилей'
} | ConvertTo-Json
try {
    $release = Invoke-RestMethod -Method Post -Headers $headers -ContentType 'application/json' `
        -Uri "$base/api/developer/products/$env:GROSSGEO_PRODUCT_ID/releases" -Body $body
    $releaseId = $release.releaseId
}
catch {
    $problem = $_.ErrorDetails.Message | ConvertFrom-Json
    if ($problem.code -ne 'VERSION_EXISTS') { throw }
    $releaseId = $problem.releaseId          # продолжаем с уже созданным черновиком
}

# 2-3. Ссылка и загрузка
$urlBody = @{ fileName = 'MyPlugin.zip'; fileType = 'Bundle' } | ConvertTo-Json
$upload  = Invoke-RestMethod -Method Post -Headers $headers -ContentType 'application/json' `
    -Uri "$base/api/developer/releases/$releaseId/files/upload-url" -Body $urlBody

Invoke-RestMethod -Method Put -Uri $upload.uploadUrl `
    -ContentType 'application/octet-stream' -InFile '.\MyPlugin.zip'

# 4. Регистрация (идемпотентна)
$regBody = @{ storagePath = $upload.storagePath; fileType = 'Bundle' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Headers $headers -ContentType 'application/json' `
    -Uri "$base/api/developer/releases/$releaseId/files/register" -Body $regBody

# 5. Отправка
Invoke-RestMethod -Method Post -Headers $headers `
    -Uri "$base/api/developer/releases/$releaseId/submit"
```

> **Готча Windows PowerShell 5.1.** `Invoke-RestMethod` возвращает массив ответов «как есть», и
> присваивание вида `$items = @(Get-Releases)` заворачивает список ещё в один массив — `foreach`
> тогда идёт по одному элементу-списку вместо элементов. Если разбираете списочные ответы,
> используйте PowerShell 7 либо разворачивайте результат явно.

## 7. Режим «Внешняя лицензия»

Продукт в режиме `ExternalLicense` вы продаёте и лицензируете сами — на своём сайте и своими ключами. Платформа —
витрина и доставка: карточка в каталоге с ценой для показа и кнопкой «Купить на сайте разработчика», установка,
обновление и удаление вашего MSI через User Panel. Участник видит на карточке пометку «Лицензия у разработчика»; в
каталоге есть фильтр «Внешняя лицензия».

| | `GrossGeo` | `ExternalOnly` | `ExternalLicense` |
|---|---|---|---|
| Кто продаёт и лицензирует | платформа | вы | вы |
| Релизы на платформе | да | нет | только MSI |
| Установка через User Panel | да | нет | да |
| Тарифы и функции | да | нет | нет |
| Пробный период | по тарифу | нет | нет |
| SDK лицензирования | нужен | не нужен | не нужен |

### Правила режима

- **Только MSI.** Релиз — `distributionType: "Installer"` с файлом `.msi`. Не переданный при создании тип становится
  `Installer`; другой тип — `INSTALLER_ONLY`. При отправке проверяются и файлы: DLL, архив или установщик не `.msi`
  среди файлов раздачи — тоже `INSTALLER_ONLY`.
- **Каждый релиз — через модератора**, даже у проверенной студии: отправка отвечает `autoApproved: false`.
- **Каналы — `Stable` и `Internal`.** `Beta` отклоняется на создании, правке и отправке: `EXTERNAL_LICENSE_NO_BETA`.
- **Лицензию платформа не выдаёт, не проверяет и не продаёт**, оплату не принимает. Проверка лицензии — в вашей
  программе.
- **Скачать и установить может любой вошедший участник** — лицензия платформы не нужна. Так раздаётся только
  релиз-MSI, прошедший модератора.
- **Тарифов и функций нет.** Создание тарифа или функции, включение отключённого тарифа, импорт `plans-manifest`,
  `defaultPlanMode` при создании продукта — `EXTERNAL_LICENSE`.
- **Пробного периода нет.** Попытка участника начать его — `TRIAL_NOT_SUPPORTED`. Исключение: если у продукта
  остались только бесплатные тарифы (в том числе выключенные), раньше срабатывает `FREE_PRODUCT`.
- **Лицензионное соглашение продукта** ([руководство](grossgeo-product-agreement-guide.md)) окно в User Panel
  показывает перед установкой и обновлением MSI. Покупка идёт на вашем сайте, вне панели, поэтому при покупке окна нет.

### Поля продукта

| Поле | Значение |
|------|----------|
| `licensingMode` | `"ExternalLicense"` |
| `externalPurchaseUrl` | Обязательно, `https://…` — адрес кнопки «Купить на сайте разработчика» |
| `externalLicenseInstructions` | Необязательно: как получить и активировать лицензию |
| `externalPrice` | Необязательно: цена для показа, `{"amount": 4900, "currency": "RUB", "period": "Year"}` |
| `clearExternalPrice` | `true` — стереть цену для показа (только правка продукта) |
| `licensingModeConfirmed` | `true` — нужен, чтобы перевести продукт **из** `ExternalLicense` в другой режим (только правка продукта) |

**Цена для показа** — только текст на карточке, платформа по ней ничего не продаёт. Задаётся целиком одним объектом:
`amount` больше нуля, не больше 100 000 000 и не точнее копеек; `currency` — три латинские буквы (код валюты, регистр
приводится к верхнему), необязательно, по умолчанию `RUB`; `period` — `Month`, `Year` или `OneTime`, обязательно. Цены нет — карточка пишет «Цена — на сайте
разработчика». Цена у продукта другого режима отклоняется, а сохранённая до смены режима наружу не показывается.

### Как включить

**Developer Panel.** Новый продукт: шаг «Лицензирование» → «На сайте студии» → флажок «Внешняя лицензия», ссылка на
покупку обязательна; цену задайте потом в форме продукта. Существующий продукт: раздел «Лицензирование» → «Режим
лицензирования» → «Внешняя лицензия», поля «URL для покупки / лицензирования», «Инструкция по активации» и «Цена для
показа на карточке» (сумма, валюта, «в месяц» / «в год» / «разово»). В форме нового релиза тип раздачи закреплён на MSI.

**API.** Создание — `POST /api/developer/products`, перевод существующего продукта — `PUT /api/developer/products/{productId}`.
Тело с `licensingMode: "ExternalLicense"`, ценой для показа или ссылкой покупки требует скоупов `products:write` и
`pricing:write`.

```bash
curl -sS -X PUT "$BASE_URL/api/developer/products/$PRODUCT_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"licensingMode":"ExternalLicense",
       "externalPurchaseUrl":"https://example.com/buy",
       "externalPrice":{"amount":4900,"currency":"RUB","period":"Year"}}'
```

Перевод в режим отклоняется, пока у продукта есть активные тарифы (`MODE_SWITCH_HAS_PLANS` — сначала отключите их) или
опубликованные либо ждущие модератора выпуски с типом раздачи не «установщик» (`MODE_SWITCH_HAS_NON_MSI_RELEASES` —
сначала отзовите их; проверяется тип выпуска, а не расширение файла).

**Обратный перевод** — только с `"licensingModeConfirmed": true` в том же теле. Без него поле `licensingMode` у продукта
в режиме `ExternalLicense` **молча игнорируется**: ответ `200`, режим прежний. Это защита от старых версий Developer
Panel, которые нового режима не знают.

| Код | Статус | Значение |
|-----|--------|----------|
| `VALIDATION_ERROR` | 400 | нет ссылки покупки или она не `https`; неверная цена для показа; цена у продукта другого режима |
| `MODE_SWITCH_HAS_PLANS` | 400 | у продукта есть активные тарифы |
| `MODE_SWITCH_HAS_NON_MSI_RELEASES` | 400 | у продукта есть опубликованные или ждущие модератора выпуски с типом раздачи не «установщик» |
| `EXTERNAL_LICENSE` | 400 | тарифы, функции, импорт `plans-manifest`, `defaultPlanMode` |
| `INSTALLER_ONLY` | 400 | релиз не MSI |
| `EXTERNAL_LICENSE_NO_BETA` | 400 | канал `Beta` |

## 8. Стабильность контракта

Публичный набор маршрутов зафиксирован и версионируется по внутренней политике версионирования (ADR-008):

- ломающее изменение выходит новым сегментом версии в пути, а не правкой существующего маршрута;
- маршрут не удаляется раньше чем через **90 дней** после пометки устаревшим;
- устаревающий маршрут отдаёт заголовок `Deprecation` — отслеживайте его в логах своей утилиты.

Маршруты, которых нет в публичной спецификации, к этим гарантиям не относятся и могут меняться
без предупреждения. Опирайтесь только на опубликованный документ.
